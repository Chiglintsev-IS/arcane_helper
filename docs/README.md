## Где что заводится

**Новое поведение.** Найти домен, которому оно принадлежит, и добавить требование в его файл. Если
поведение задевает несколько доменов — оно принадлежит сценариям, а не одному из них.

**Новое понятие домена.** Сначала строка в глоссарии с именем в коде, потом
использование. Это защищает от расхождения «ячейка / слот / заряд» в одной кодовой базе.

**Техническая развилка.** Запись `ADR` в [decisions.md](decisions.md): решение, причина, цена.
Решение, принятое молча в коде, считается непринятым. Продуктовая договорённость — правило стола,
устройство экрана, граница продукта — записывается в [agreements.md](agreements.md) тем же форматом.

**Неизвестное правило или число.** Запись `OQ-##` в открытых вопросах. Угадывать механику
запрещено.

## Формат требования

Требование определяется ровно один раз, в документе своего домена. Перед заголовком ставится явный
якорь `<a id="fr-070"></a>`: по нему на требование ссылаются, и он переживает правку заголовка.

```markdown
### FR-070 — Ячейки Торна

**Статус:** Готово · **Проверка:** unit `spellSlotsForLevel`

Текст требования в изъявительном наклонении: что система делает.
```

Как эти документы пишутся — язык, словарь статусов, владение фактом, запрет на историю и на имена из
кода — сказано в [CLAUDE.md](../CLAUDE.md), и здесь не повторяется: правило, названное дважды,
расходится с собой на первой же правке. Целостность спеки держит `npm run verify`.
