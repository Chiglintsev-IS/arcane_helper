## Регламент изменений

**Добавляю функциональность.** Найти подходящую фичу в [реестре](features/README.md). Добавить
требование `FR-###` со следующим свободным номером в её файл. Если фича новая — создать
`features/F-##-slug.md` по образцу существующих и добавить строку в реестр. Указать статус `План`.

**Меняю поведение.** Отредактировать текст требования, а не приписывать исключение в код. Если
старое поведение больше не нужно — статус `Отменено` с одной строкой причины.

**Принимаю техническое решение.** Записать `ADR` в [decisions.md](decisions.md): контекст, варианты,
выбор, последствия. Решение, принятое молча в коде, считается непринятым.

**Ввожу новый термин.** Сначала строка в [глоссарии](glossary.md) с именем в коде, потом
использование. Это защищает от расхождения «ячейка / слот / заряд» в одной кодовой базе.

**Не знаю правило или число.** Запись `OQ-##` в [open-questions.md](open-questions.md) с пометкой,
блокирует ли она разработку. Угадывать механику запрещено.

**Закрываю требование.** Статус `Готово` — когда код написан. `Проверено` — когда прошёл тест или
игровая сессия, указанные в разделе «Проверка» фичи.

## Проверка целостности

```bash
python3 scripts/check-docs.py
```

Скрипт проверяет то, что легко ломается при правках вручную: висячие ссылки и якоря, требования,
которые упоминаются но нигде не определены, расхождение реестра фич с фактическими требованиями,
потерянные требования ТЗ и статусы вне словаря. Запускать после каждой правки спеки; после появления
Node-проекта — перенести в CI рядом с проверкой контента заклинаний.

## Соглашение о формате

Каждый документ начинается с заголовка, строки статуса и назначения. Требования оформляются
однотипным блоком:

```markdown
### FR-001 — Короткое имя требования

**Статус:** План · **Источник:** ТЗ §9.1 · **Проверка:** unit `spellSaveDc`, AC-09

Текст требования в изъявительном наклонении: что система должна делать.
```

Ссылки между документами — относительные, чтобы работали и в IDE, и на GitHub.
