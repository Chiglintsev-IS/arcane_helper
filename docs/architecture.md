# Техническая архитектура

## Формат приложения

Progressive Web Application. Обоснование выбора — [ADR-0001](decisions.md#adr-0001).

Следствия: установка на домашний экран без App Store, офлайн-работа, быстрые обновления, единая
кодовая база, возможность последующей упаковки в нативную оболочку.

## Стек

| Слой | Технология | Роль |
|---|---|---|
| Каркас | Next.js | Статическая сборка, маршрутизация, PWA-обвязка |
| Интерфейс | React + TypeScript | Компоненты |
| Стили | Tailwind CSS | Оформление, размеры зон нажатия, тема |
| Состояние | Zustand | Рантайм-состояние персонажа и черновика применения |
| Формы | React Hook Form | Подготовка заклинаний, настройки, ручные правки |
| Схемы | Zod | Валидация контента и импорта, вывод типов |
| Хранение | IndexedDB через Dexie.js | Персистентное состояние и контент |
| Офлайн | Web App Manifest + Service Worker | Установка и кэширование |
| Тесты | Vitest, React Testing Library, Playwright, axe-core | Unit, компонентные, E2E, доступность |

Обоснование ключевых выборов: [ADR-0002](decisions.md#adr-0002) (Next.js и статический экспорт),
[ADR-0003](decisions.md#adr-0003) (Zustand + Dexie), [ADR-0004](decisions.md#adr-0004) (Zod как
единственный источник схем).

## Принципы

Проект живёт долго и меняется от игры к игре: правила уточняет мастер, состав заклинаний — игрок.
Поэтому дешевизна изменения важнее краткости кода сегодня. Два правила, из которых всё остальное
выводится.

**Простота (KISS).** Абстракция вводится, когда у неё есть второй потребитель, а не в ожидании его.
Один способ сделать вещь вместо двух. Если выбор между «сложнее и точнее» и «проще и достаточно» —
проще, а разница записывается в спеку.

**Разделение ответственности (SOLID) там, где меняется чаще всего.** Пять принципов в этом проекте
означают конкретное:

| Принцип | Что означает здесь |
|---|---|
| Единственная ответственность | `rules/` считает, `store/` меняет состояние, `components/` показывает. Формула не знает о React, состояние не знает о базе |
| Открытость к расширению | новая операция над состоянием не требует правок в существующих: снимок отмены вычисляется сравнением, а не пишется руками ([ADR-0006](decisions.md#adr-0006)) |
| Подстановка | хранилище описано портом, у которого две взаимозаменяемые реализации, и обе проходят один и тот же набор тестов ([ADR-0009](decisions.md#adr-0009)) |
| Разделение интерфейсов | порт хранилища — три метода, а не «всё, что умеет база» |
| Инверсия зависимостей | состояние зависит от порта, а не от Dexie; браузерная база — деталь, заменяемая без правок логики |

**Практическая проверка.** Изменение правила должно требовать правки в одном месте: числа — в
`rules/`, поведение — в `store/`, текст — в контенте. Если правка расходится по трём файлам, дело в
структуре, а не в правке.

## Подходы

Проект собирает несколько известных подходов, и у каждого своя зона: они не спорят, потому что
отвечают на разные вопросы. Подход, применённый вне своей зоны, и есть каша.

| Подход | За что отвечает здесь |
|---|---|
| DDD | границы: домен разбит на ограниченные контексты со своими агрегатами и инвариантами; рёбра между контекстами — явный список в проверке границ |
| Гексагональная архитектура | направление зависимостей: правила внутри, технологии снаружи; входящие адаптеры отделены от исходящих ([ADR-0041](decisions.md#adr-0041)) |
| Сообщения через границу | ядро и отображение говорят командами, снимком и отказом ([ADR-0039](decisions.md#adr-0039)); договор — отдельный корень, клиент один, провода два ([ADR-0040](decisions.md#adr-0040)) |
| CQRS | запись — командами через агрегат, чтение — проекциями снимка; отдельного хранилища чтения нет: производное не хранится, проекция — функция состояния |
| Feature-Sliced Design | организация отображения: слои и слайсы, импорт только вниз |

Источник истины — состояние, а не события: лог остаётся механизмом обратимости ограниченной
глубины, хранилище событий рассмотрено и отвергнуто ([ADR-0043](decisions.md#adr-0043)). Сценарии
группируются предметно — применение, отдых, здоровье, — а не по каталогу на команду
([ADR-0041](decisions.md#adr-0041)).

## Требования к устройству

Действуют везде, где есть производная величина, вклад в неё или конфликт состояния. Нарушение —
дефект структуры, а не тема для обсуждения при каждой задаче.

- **Производное не хранится.** Итог — функция состояния; хранится только невыводимое. Хранимая
  копия производного расходится с источником молча.
- **Поток направлен: база → вклады → итог.** Считающий — сток графа: он не импортирует поставщиков
  вкладов, поставщики не знают его; сводит их сценарий.
- **У отклонения одна форма.** Вещь, заклинание, зелье и слово мастера для счёта неразличимы: в
  контракте нет признака отправителя. Новый род источника не меняет в счёте ни строки.
- **Имена, правила, механизм — три ответственности.** Словарь имён не знает правил; правила не
  знают источников вкладов; механизм свёртки — ни правил игры, ни имён величин.
- **Расширение — добавлением.** Новое понятие — новый модуль и строка словаря; существующее не
  правится. Карту собирает сборщик, который знает каждого и которого не знает никто.
- **Запрет невыразим, а не обнаружим.** Недопустимое не собирается: закрытые конструкторы, порядок
  объявления, типизированные читатели. Данные контента стережёт разбор при загрузке, отказ называет
  виновника; прогон — страховка, не основная защита.
- **Ацикличность — критерий границы.** Модули делятся по ответственности; цикл при таком делении —
  неверная граница, а не повод для инверсии: порт прячет цикл от проверки, а не запрещает. Порт —
  для пересечения границы ответственности (время, хранилище, случайность).
- **Считающему приносят — он не спрашивает.** Расчёт не читает чужого состояния; применимость
  проверяется по составу принесённого.
- **Данные отделены от правил.** Контент несёт факты о себе; формулы и пределы — у владельца
  величины. Правило меняется без правки контента, контент заводится без знания формул.
- **Приложение не решает за игрока.** Противоречие состояния — отказ с причиной словами, а не тихий
  выбор из конфликтующих. Правило игры, называющее выгодный вариант, считается молча.
- **База хранится, слои снимаются.** У слоя есть игровое окончание, у правки базы — нет; правка
  базы — переход, обратимый логом.
- **Предпросмотр — чистая функция.** «Что будет, если» — добавление вклада в счёт, а не изменение
  состояния: запрет менять состояние до подтверждения выполняется устройством.

## Слои

Приложение делится на три корня: договор, логика и отображение. То, что сегодня всё исполняется в
одном браузере, ничего не меняет — граница проходит по ответственности, а не по месту исполнения, и
устроена так, чтобы логика целиком переехала в отдельный процесс одним выбором провода
([ADR-0040](decisions.md#adr-0040)).

```
src/
  app/                Next App Router: маршрут страницы и маршруты бэкенда, по три строки каждый
  contract/           договор ядра и отображения: команды, снимок, отказ, порт, провод, клиент
  core/               логика — гексагональная архитектура
    domain/           сущности, объекты-значения, агрегаты, инварианты
      shared/         основа: границы уровней, примитивы схем, отказ с причиной, пул ресурса
    application/      сценарии (юз-кейсы) и порты; про договор не знает
    presentation/     входящие адаптеры: разбор команды, вызов сценария, проекции снимка
    infrastructure/   исходящие адаптеры: Dexie, память, часы, встроенный каталог
  shared/             язык: морфология, названия спасбросков, сокращения монет, размер кости
  ui/                 отображение — Feature-Sliced Design
    app/              оболочка и сборка: провайдеры, выбор провода, панель режимов
    screens/          экраны: по одному на режим
    widgets/          составные блоки: шапка ресурсов, мастер применения, подробная карточка
    features/         действия: фильтры, отдых, реакции, отыгрыш, обмен данными
    entities/         показ сущностей: карточка заклинания, концентрация, сессия
    shared/           примитивы, тона, контекст сторов, признаки строки списка
```

**Правило зависимостей.** Стрелки ведут внутрь: договор не импортирует ничего; домен — только себя и
язык; сценарии — домен; представление — договор, сценарии и домен; инфраструктура — порты и домен.
Язык стоит отдельным корнем и не знает никого: по-русски говорят обе стороны, и вторая копия
склонения разошлась бы с первой молча.
Отображение видит из логики только договор. Исключений три, и каждое названо в проверке поимённо:
композиционный корень, который собирает целое; прогонная сборка сторов, поднимающая настоящее ядро на
хранилище в памяти; язык, на котором говорят обе стороны. Четвёртое означало бы, что правило
перестало проверять границу. Внутри `ui/` импорт идёт только вниз по слоям, слайсы одного слоя друг о
друге не знают.

**Статус.** Правило включено в проверку границ ([ADR-0046](decisions.md#adr-0046)): протечка обратно
невозможна — импорт логики в экране падает прогоном, а не замечается на ревью. Считается и
отложенный импорт: он приводит модуль в ту же поставку, только позже.

**Две поставки.** Способ доставки сообщений выбирается одной переменной сборки, и она же решает,
собирается ли приложение статическим экспортом: обработчиков маршрутов он не исполняет, и бэкенду
было бы негде отвечать ([ADR-0047](decisions.md#adr-0047)). Логику композиционный корень берёт
отложенным импортом, поэтому страница, выбравшая сеть, не загружает ни одного модуля логики и
состояния у браузера в ней нет вовсе. Сессия бэкенда одна, живёт в памяти процесса и перезапуска не
переживает ([ADR-0059](decisions.md#adr-0059)). Офлайн-экспорт остаётся основной поставкой.

**Логика — только в `core/`.** Любое вычисление по правилам игры (тариф, стоимость, лимит,
производная величина) идёт через сценарий или метод агрегата домена. `ui/` вызывает готовый
результат и показывает его; он не пересчитывает и не дублирует формулу у себя, даже ради одной
строки кода.

**Наружу ведёт явный путь.** Символ выдаёт только его владелец: реэкспортов и барелей нет.
Посредник, пересдающий чужой символ под своим адресом, стирает из импортов сам факт пересечения
границы; пока путь ведёт к владельцу, каждая протечка названа в самом импорте.

Правила зависимостей — проверка, а не договорённость: `npm run check:layers`. Она же запрещает коду
ссылаться на документацию путём или номером требования — такие ссылки ломаются молча.

## Состояние и хранение

**Рантайм.** Zustand хранит `CharacterState`, лог и черновик применения. Черновик — отдельный
стор: это техническая гарантия инварианта [FR-022](scenarios.md#fr-022), а не
договорённость.

**Мутации только через действия стора.** Каждое действие создаёт запись лога со снимком отмены
([ADR-0006](decisions.md#adr-0006)); прямая правка состояния из компонентов ломает обратимость.
Дверь одна, и стережёт её не память: тип состояния глубоко неизменяем — присваивание в поле не
собирается, правка возможна только новым состоянием через агрегат; запись лога принимает
только корень агрегата, не голое состояние; проверка границ следит, что полное состояние собирается
из полей владельцев.

**Единица записи — команда.** Она несёт идентификатор намерения, и повтор одной команды — обрыв
доставки, двойное нажатие — не применяется дважды: повтор узнаётся логом и отвечает текущим
снимком ([ADR-0042](decisions.md#adr-0042)).

**Целость гарантирует агрегат, а не тот, кто его просит.** Правка приходит параметрами и уходит
либо новой сущностью, либо отказом с причиной словами. Числа проверяются теми же объявлениями, что
и сохранённое состояние, — второго правила о том же факте нет. Экран ничего не проверяет: передаёт
набранное, показывает ответ, полученную сущность считает целой.

**Персистентность.** Каждое изменение пишется в IndexedDB немедленно
([ADR-0003](decisions.md#adr-0003)): дебаунс терял бы последнее действие, а состояние — единицы
килобайт. Хранилище скрыто портом из трёх методов ([ADR-0009](decisions.md#adr-0009)); реализации —
браузерная и в памяти — проходят один набор тестов, логика проверяется без браузера.

**Контент.** Заклинания хранятся в JSON в репозитории, проходят валидацию Zod при сборке и приходят к
игроку вместе со сборкой. Встроенный каталог в хранилище не записывается: его копия заморозила бы
книгу на дате установки, и обновление приложения перестало бы приносить новые карточки
([ADR-0019](decisions.md#adr-0019)). В хранилище попадает только каталог, импортированный игроком
([FR-123](domains/catalog.md#fr-123)). Пользовательские дополнения (заметки, свои варианты отыгрыша)
живут в состоянии персонажа и не перезаписываются обновлением контента.

**Миграции.** Схема БД версионируется средствами Dexie. Миграция обязана сохранять пользовательские
данные ([NFR-003](data-exchange.md#nfr-003)); удаление таблицы с состоянием при обновлении
недопустимо.

## PWA и офлайн

**Манифест.** `display: standalone`, иконки под iOS, цвет темы, `orientation: portrait`.

**Service Worker.** Стратегии:

| Ресурс | Стратегия | Почему |
|---|---|---|
| Оболочка приложения (HTML, JS, CSS) | precache, cache-first | Мгновенный старт офлайн |
| Шрифты и иконки | cache-first | Не меняются |
| Контент заклинаний | precache | Обязателен офлайн ([NFR-002](data-exchange.md#nfr-002)) |
| Внешние запросы | отсутствуют | Приложение не обращается к сети в рантайме |
| Обращения к бэкенду | мимо кэша | Снимок не статика: из кэша он показывал бы вчерашнюю игру |

Сетевых запросов в рантайме нет вовсе — это самая надёжная стратегия офлайна и заодно гарантия
приватности: данные не могут утечь, поскольку их некуда отправлять. Это свойство офлайн-поставки, и
она остаётся основной. Поставка с выделенным бэкендом — отдельная сборка
([ADR-0047](decisions.md#adr-0047)): приложение в ней говорит только со своим бэкендом, игра живёт
на его стороне, и офлайн-обещания на неё не распространяются.

**Обновление.** Новый service worker не активируется молча: пользователю показывается предложение
перезагрузить. Перезагрузка посреди мастера применения потеряла бы черновик.

## Тестирование

Технически:

- Vitest — движок правил и сторы; движок покрывается полностью, поскольку это место, где ошибка
  означает неверную игру;
- React Testing Library — компоненты с логикой (фильтры, шаги мастера);
- Playwright — сценарии UC-01…UC-05 в мобильных viewport, включая офлайн-режим;
- axe-core — базовая доступность экранов.

## Ограничения платформы

**Safari на iOS.** IndexedDB может быть очищена системой при нехватке места. Отсюда обязательность
экспорта и предупреждение в настройках.

**Буфер обмена.** Запись в буфер требует пользовательского жеста: копирование выполняется
синхронно по нажатию.

**Отсутствие фоновой работы.** Таймеры и уведомления в установленном PWA на iOS ненадёжны — ещё одна
причина не отсчитывать длительность эффектов автоматически в MVP.

## Роль ИИ

ИИ не касается механики: правила и числа хранятся структурированно и проверены вручную. В будущих
версиях ИИ допустим только для художественного слоя поверх проверенной механической карточки
([ADR-0005](agreements.md#adr-0005)).
