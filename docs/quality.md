**AC-01 и AC-02 проверяются руками, на телефоне.** Установку с иконки автоматика не выполняет
вовсе, а прогон `serves the app from cache when the network is gone` глушит сеть маршрутом и
доказывает только ответ из кэша: перезагрузку под перехватом сети WebKit не делает. Оба критерия
закрывает игровая сессия.

**Уточнение AC-03.** Числа взяты из состава книги и держатся тестом
`состоит из 29 карточек: 4 заговора и 25 заклинаний по уровням`. В ТЗ было 18 заклинаний — состав
расширен игроком, и критерий следует за книгой, а не за исходной цифрой.

**Уточнение AC-10.** Минимум три варианта отыгрыша проверяются по одному прогону на карточку:
`«Луч холода» имеет минимум контента по FR-050` и ещё 28 таких же. Управление вариантами
([FR-053](domains/spellbook.md#fr-053)) в критерий не входит и остаётся несделанным.

**Уточнение AC-20.** Блок отыгрыша содержит ровно одну механическую строку — что из отыгрыша
обязательно по правилам ([ADR-0011](decisions.md#adr-0011)). Всё остальное в нём художественное, и
оформление у блока заведомо другое.

## Модульные тесты

Обязательно покрываются: расчёт КС заклинаний; расчёт атаки заклинанием; расходование ячеек; повышение
уровня заклинания; лимит подготовки; ритуальное применение; переключение концентрации; расчёт КС
концентрации; восстановление после отдыха; доступность реакции.

Движок правил покрывается полностью: это единственное место, где
ошибка означает неверно проведённую игру, и она не проявится как сбой — только как неправильное число.

Отдельно применяется property-based тестирование там, где важна симметрия операций:

- любая последовательность списаний и возвратов ячеек возвращает исходное состояние;
- применение действия и его отмена дают состояние, побитово равное исходному;
- цикл экспорт → импорт даёт идентичное состояние.

## Интеграционные тесты

Сценарии: применение обычного заклинания; применение заговора; применение реакции; применение ритуала;
применение повышенной ячейкой; замена концентрации; отмена последнего действия; восстановление
состояния после перезапуска.

Дополнительно проверяются инварианты, которые нельзя проверить unit-тестом:

- до подтверждения в мастере состояние персонажа не изменилось ([FR-022](scenarios.md#fr-022));
- подтверждение применяет все пять эффектов атомарно ([FR-023](scenarios.md#fr-023));
- провал импорта не изменяет существующие данные ([FR-122](data-exchange.md#fr-122));
- обновление версии приложения сохраняет пользовательские данные ([NFR-003](data-exchange.md#nfr-003)).

## E2E-тесты

Сценарии UC-01…UC-05 выполняются в мобильном viewport iPhone SE в WebKit. Он
обязательный: на нём проверяется требование «ключевая механика без прокрутки». Остальные размеры
добавляются по мере надобности — пока вёрстка одна, три прогона одного и того же сценария только
удлиняют сборку.

Отдельный прогон работы без сети ([NFR-001](data-exchange.md#nfr-001)) проверяет ответ из
кэша при заглушённой сети, а не полное открытие приложения в офлайне: перезагрузку под перехватом
WebKit не выполняет. Разницу закрывает игровая сессия (AC-02).

Измеряемое в E2E:

- число нажатий до технической инструкции ≤ 2 ([M-02](product.md#метрики));
- число основных шагов применения ≤ 4 ([M-03](product.md#метрики));
- путь от триггера реакции до результата ≤ 2 нажатий.

## Проверка контента

Скрипт в CI, а не ручная вычитка, проверяет:

- все 29 карточек проходят Zod-схему, включая инварианты из ;
- минимум художественного контента [FR-050](domains/catalog.md#fr-050) выполнен для каждого;
- в текстах отыгрыша нет стоп-слов из `prohibitedThemes` (огонь и производные);
- реплики не длиннее `maximumPhraseLength`;
- `announcementTemplate` не содержит текста из `roleplay` ([FR-042](scenarios.md#fr-042));
- ключи `damage.scaling` не ниже уровня заклинания;
- каждый идентификатор в подготовленном наборе существует в книге заклинаний.

## Доступность

axe-core прогоняется в E2E на семи экранах — бой, карточка заклинания, мастер применения, привал,
экран реакций, журнал, магическое восстановление — с наборами правил `wcag2a`, `wcag2aa`, `wcag21a`,
`wcag21aa`. Всё это один прогон `combat screen, spell card and wizard pass axe-core`. Первый прогон
нашёл настоящую проблему: цветные метки и кнопки не давали контраста 4.5:1, потому что цвета были
подобраны под тёмную тему. Отсюда тёмные варианты цветов для светлой темы в `globals.css`.

Плюс ручные проверки, которые axe не покрывает:

- информация различима без цвета — монохромный режим;
- зоны нажатия ≥ 44 × 44 px, включая элементы списков;
- вёрстка не ломается при увеличенном системном шрифте;
- тёмная тема читаема.

## Игровое тестирование

MVP должен пройти минимум две реальные игровые сессии. Это единственная проверка, которую невозможно
автоматизировать, и главный источник исправлений.

После каждой сессии фиксируются: действия, занявшие слишком много времени; непонятные формулировки;
недостающие предупреждения; лишние шаги; ошибки в механике; неиспользуемые элементы интерфейса.

Результаты сессии превращаются в изменения спеки (новые или изменённые `FR`), а не в правки кода
напрямую — иначе спека перестанет отражать приложение после первой же игры.

## Где названы прогоны

Прогон, доказывающий требование, назван в строке «Проверка» самого требования — там, где требование
и живёт. Второй таблицы с теми же именами нет: она расходилась с кодом при первом же переименовании
прогона, и молча.

Колонки соответствия «критерий → требования» хватает таблицы критериев выше. Обратное соответствие
получается поиском по номеру.

Название с круглыми скобками при точечном прогоне экранируется: `-t` принимает регулярное выражение.
