# F-10 — Журнал боя и отмена

> Статус: Готово · Этап: 2 · Обновлено: 2026-07-31
> Требования: FR-110…FR-112 · Сценарии: все · Источник: ТЗ §9.12

## Зачем

Игрок нажимает не то, мастер меняет решение, заклинание отменяется контрзаклинанием. Без отмены
приложение из помощника превращается в источник неверного состояния, которое приходится править
вручную. Журнал — механизм обратимости, а не история кампании.

## Требования

<a id="fr-110"></a>
### FR-110 — Состав журнала

**Статус:** Готово · **Проверка:** интеграционный `journal records all state changes`

Система должна сохранять последние действия: применение заклинания; потраченную ячейку; начало
концентрации; завершение концентрации; применение реакции; восстановление ресурсов.

Каждая запись содержит достаточно данных для обратной операции — снимок затронутых полей до изменения,
а не только тип события.

<a id="fr-111"></a>
### FR-111 — Отмена последнего действия

**Статус:** Проверено · **Проверка:** интеграционный `отмена возвращает потраченную ячейку`, [AC-17](../quality.md#критерии-приёмки-mvp)

Пользователь должен иметь возможность отменить последнее действие.

<a id="fr-112"></a>
### FR-112 — Журнал не является логом кампании

**Статус:** Готово · **Проверка:** unit `journal trims to limit`

Журнал не должен использоваться как полноценный лог всей игровой кампании.

Хранится ограниченное число последних записей; старые вытесняются. Значение лимита —
[OQ-08](../open-questions.md#oq-08).

## Поведение и крайние случаи

**Одна запись на одно пользовательское действие.** Подтверждение применения заклинания списывает
ячейку, тратит действие, запускает концентрацию и создаёт эффект — это одна запись журнала и одна
отмена. Пользователь думает в терминах «я применил заклинание», а не «я изменил четыре поля».

**Отмена только последнего.** Выборочная отмена из середины истории не поддерживается: состояния
зависят друг от друга, и точечный откат даёт противоречивое состояние. Многократное нажатие отменяет
по одному действию назад.

**Отмена отмены.** Не поддерживается в MVP. Повторное применение заклинания дешевле, чем корректный
redo-стек.

**Что не попадает в журнал.** Навигация, фильтры, выбор варианта отыгрыша, заметки — не изменяют
игровое состояние и журнал не засоряют.

**Долгий отдых.** Отменяем, как и всё остальное: запись хранит полный снимок ячеек, концентрации и
эффектов до отдыха. Это самая тяжёлая запись журнала и единственная, где снимок близок к полному
состоянию.

**Ручные правки.** Изменения через «Мастер решил иначе» и ручную правку ресурсов
([FR-142](F-06-resources.md#fr-142)) тоже журналируются: они ошибочны не реже автоматических.

**Переживание перезапуска.** Журнал хранится вместе с состоянием, поэтому отмена доступна и после
закрытия приложения ([AC-18](../quality.md#критерии-приёмки-mvp)).

## Проверка

| Что проверяем | Как |
|---|---|
| Каждое событие FR-110 создаёт запись | Интеграционный, по одному сценарию на событие |
| Отмена возвращает состояние побитово | Property-based: применить → отменить → сравнить со снимком |
| Одно применение заклинания = одна отмена | Интеграционный |
| Отмена долгого отдыха восстанавливает ячейки, концентрацию и эффекты | Интеграционный |
| Отмена доступна после перезапуска | E2E с перезагрузкой страницы |
| Журнал не растёт бесконечно | Unit |
