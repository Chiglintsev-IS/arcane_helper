# Правила работы в этом репозитории

## С чего начать

Прочитай [docs/roadmap.md](docs/roadmap.md): там состояние на сегодня, следующий шаг и чего не хватает
в логике. Затем [docs/features/README.md](docs/features/README.md) — реестр фич со статусами.

Быстрая проверка, что репозиторий в порядке:

```bash
npm run check:docs && npm run typecheck && npm run test:coverage && npm run build
```

## Что это за проект

Arcane Helper — оффлайн PWA-помощник по применению и отыгрышу магии в бою D&D 5e (2014).
Первый и единственный персонаж MVP — Торн, волшебник 7 уровня. Полное описание — в [docs/](docs/README.md).

## Спека — источник истины

Документация в `docs/` управляет проектом, а не описывает его пост-фактум.

1. **Сначала спека, потом код.** Новое поведение сначала появляется как требование в файле фичи,
   затем реализуется.
2. **Один коммит — код и спека вместе.** Если поведение изменилось, а `docs/` не изменился, коммит
   неполный.
3. **Нет требования — нет фичи.** Код, который не следует ни из одного FR/NFR, либо лишний, либо
   требование забыли записать.
4. **Не выдумывать игровую механику.** Числа, КС, урон, длительности берутся из подтверждённых
   источников и хранятся структурированно. При сомнении — не угадывать, а добавить запись в
   [docs/open-questions.md](docs/open-questions.md).
5. **ИИ не трогает механику.** Художественный текст (реплики, жесты, описания) отделён от
   механических полей и не может их изменять. См. [ADR-0005](docs/decisions.md#adr-0005).

После правки спеки — прогнать проверку целостности:

```bash
python3 scripts/check-docs.py
```

Она ловит висячие ссылки, требования без определения, расхождение реестра фич с фактическими
требованиями и потерянные требования ТЗ.

## Схема идентификаторов

| Префикс | Что обозначает | Где живёт |
|---|---|---|
| `F-##` | Фича (единица планирования и поставки) | `docs/features/F-##-*.md` |
| `FR-###` | Функциональное требование | внутри файла фичи |
| `NFR-###` | Нефункциональное требование | внутри файла фичи |
| `UC-##` | Пользовательский сценарий | `docs/use-cases.md` |
| `AC-##` | Критерий приёмки MVP | `docs/quality.md` |
| `ADR-####` | Принятое техническое решение | `docs/decisions.md` |
| `OQ-##` | Открытый вопрос | `docs/open-questions.md` |
| `M-##` | Продуктовая метрика | `docs/product.md` |

Идентификаторы не переиспользуются. Отменённое требование помечается статусом `Отменено`, но номер
остаётся на месте, чтобы ссылки из истории не ломались.

## Статусы

Единый словарь для требований, фич и этапов: `План` → `В работе` → `Готово` → `Проверено`.
Дополнительно: `Отложено` (вне MVP, решение зафиксировано), `Отменено` (не будет реализовано).

`Проверено` ставится только после прохождения теста или игровой сессии, указанных в разделе
«Проверка» соответствующей фичи.

## Язык

- Документация, интерфейс, контент заклинаний — **русский**.
- Код, идентификаторы, имена файлов, сообщения коммитов — **английский**.
- Глоссарий связывает русский термин, английский оригинал правил и имя в коде. Имена в коде берутся
  только из глоссария — не изобретать синонимы (`slot`/`cell`/`charge` для одного и того же).

## Технический контур

Стек и его обоснование — в [docs/architecture.md](docs/architecture.md) и `ADR-0001..0004`.
Кратко: Next.js + TypeScript + Tailwind, Zustand для рантайм-состояния, Dexie/IndexedDB для
хранения, service worker для офлайна, Vitest + Playwright для тестов.

Инварианты, которые нельзя нарушать в коде:

- До подтверждения в мастере применения состояние персонажа не меняется (`FR-022`).
- Любое расходование ресурса обратимо через журнал (`FR-111`).
- Одновременно активна не более одной концентрации (`FR-080`).
- Обновление приложения не удаляет пользовательские данные (`NFR-003`).
